# cometa

Сервис для отправки рекламных настроек в API Cometa на основе данных из Google Sheets.

## 1. Назначение проекта

`cometa` автоматизирует массовое обновление настроек рекламных кампаний:

- читает строки из Google Sheets;
- валидирует и нормализует данные;
- формирует payload для API Cometa;
- отправляет payload батчами;
- обрабатывает ошибки API с сохранением максимально возможного объема валидных данных.

Основной бизнес-сценарий: регулярная синхронизация настроек автопилота по артикулам без ручного редактирования в интерфейсе API.

## 2. Общая схема работы

Поток выполнения при `python run.py`:

1. Entry point создает `AutopilotManager`.
2. Менеджер настраивает логирование и загружает `.env`.
3. Читаются данные из Google Sheets (лист с настройками автопилота).
4. Каждая строка валидируется и преобразуется в модель.
5. Невалидные/пустые для обновления строки исключаются и логируются.
6. Валидные записи собираются в `final_payload`.
7. `final_payload` режется на батчи по 1000 записей.
8. Каждый батч отправляется в API.
9. При специальной ошибке `Артикул не найден` проблемный артикул удаляется только из текущего батча, и батч отправляется повторно.
10. Логи выполнения и ошибок пишутся в `logs/`.

## 6. Работа с Google Sheets

Источник данных:

- клиент: `clients/google_sheets_client.py`;
- credentials: `creds/creds.json`;
- имя таблицы: `Панель управления продажами Вектор`;
- имя листа: `Настройки автопилота`.

Ожидаемые колонки (фактически из `row_parser.py`):

- `Артикул`
- `Идентификатор юрлица`
- `Активность`
- `Минимальный расход`
- `Максимальный расход`
- `Целевой ДРР`
- `Дата, начиная с которой будет действовать целевой ДРР`

Поведение:

- строки без обязательных ID исключаются;
- строки без изменений (только `api_key_id` + `product_id`) исключаются;
- исключения логируются.

## 7. Валидация данных

Проверки выполняются в `services/processing/row_parser.py` и `services/autopilot_manager.py`:

1. Парсинг обязательных полей `Артикул` и `Идентификатор юрлица` в `int`.
2. Парсинг числовых полей (`Минимальный расход`, `Максимальный расход`, `Целевой ДРР`).
3. Обработка `nan`, пустых строк, пробелов, `\xa0`, запятой как десятичного разделителя.
4. Если после формирования payload нет обновляемых полей, строка считается пустой для обновления.

Куда пишутся исключения:

- `logs/excluded_articles.log` (через `ExclusionLogger` и logging filter).

Примечание:

- исторического отдельного файла `excluded_rows.log` в новой схеме нет; исключения также идут в `logs/excluded_articles.log`.

## 8. Batch processing

В проекте батч — это список payload-элементов, отправляемых одним HTTP-запросом.

- Размер батча: `1000` (задан в `AutopilotManager.run`).
- Формирование: слайсами из `final_payload`.
- Успех: HTTP `200`.
- При проблеме внутри батча применяется локальная фильтрация проблемного артикула (см. следующий раздел).

## 9. Обработка ошибки «Артикул не найден»

Критичный сценарий реализован в:

- `clients/cometa_api_client.py` — извлечение `article_id` из `detail`;
- `services/batch/batch_sender.py` — повторная отправка батча.

Алгоритм:

1. API возвращает `400` с `detail: "Артикул не найден: <id>"`.
2. Из `detail` извлекается `<id>`.
3. Из текущего батча удаляются все элементы с `product_id == <id>`.
4. Исключение логируется.
5. Этот же батч отправляется повторно.
6. Цикл повторяется, пока:
   - батч не отправится успешно;
   - или батч не станет пустым;
   - или ошибка не станет необрабатываемой (другой тип).

Ограничения:

- ошибки других типов **не маскируются**;
- если батч полностью очищен, это явно логируется;
- проблемные артикулы нужно отдельно проверять в источнике данных и в API.

## 10. Логирование

Логирование централизовано в `services/logging_setup.py`.

Папка логов:

- `logs/` (создается автоматически).

Файлы:

- `logs/processing.log` — общий поток выполнения;
- `logs/api_errors.log` — ошибки API;
- `logs/excluded_articles.log` — исключенные строки/артикулы.

Ротация:

- ежедневно в полночь (`TimedRotatingFileHandler`, `when="midnight"`).

Retention:

- `14` ротаций (по умолчанию `retention_days=14`).

## 11. .gitignore

В проекте исключены из git:

## 13. Типовые проблемы и диагностика

### Не читается Google Таблица

- Проверьте путь `creds/creds.json`.
- Проверьте, что сервисный аккаунт добавлен в доступ к таблице.
- Проверьте точное имя таблицы и листа.

### Ошибка авторизации Google API

- Невалидный/чужой JSON credentials.
- Сервисный аккаунт не имеет прав.

### API 400

- Смотрите `logs/api_errors.log` и `logs/processing.log`.
- Для `Артикул не найден` проверьте `logs/excluded_articles.log`.

### Батч не отправляется

- Проверить `COMETA_API_KEY`.
- Проверить сетевой доступ к `https://api.e-comet.io/v1/autopilots`.
- Проверить, не изменился ли формат ответа API.

### Пустой набор данных к отправке

- Проверьте, что в таблице есть строки с обязательными ID и заполняемыми полями.

### Нет `.env`

- Создайте `.env` в корне и добавьте `COMETA_API_KEY`.

### Не создаются логи

- Проверьте права записи в директорию проекта.
- Проверьте, что вызывается `configure_logging()`.

### Проблемы с путями на Windows

- Запускайте из корня проекта `cometa`.
- Не используйте относительные пути из другой директории.

## 14. Как развивать проект дальше

Рекомендации:

- новые API-интеграции добавлять в `clients/`;
- новые правила валидации — в `services/processing/`;
- новые модели payload — в `models/`;
- сложные сценарии отправки — в `services/batch/`;
- не переносить бизнес-логику в `run.py`;
- сохранять `AutopilotManager` как orchestration-слой.

## 15. Для разработчика

Правила работы:

1. Не менять формат входных колонок Google Sheets без необходимости.
2. Не ломать сценарий запуска `python run.py`.
3. Не коммитить секреты (`.env`, credentials).
4. Для нетривиальной логики писать docstring и короткие комментарии «почему».
5. Сохранять текущий стиль логирования и раздельные лог-файлы.
6. После изменений в batch-логике проверять сценарий `Артикул не найден`.
